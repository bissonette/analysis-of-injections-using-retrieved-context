# Архитектура проекта

Проект реализует **контроль разрешений retrieved-контекста** в RAG-системе: вместо бинарного
вопроса «атака или нет» для каждого retrieved-фрагмента определяется, **какие виды влияния на
ответ модели этот фрагмент имеет право оказывать**. Фрагмент, выходящий за рамки того, что ему
разрешил запрос пользователя, блокируется или очищается до передачи в LLM.

## Виды влияния фрагмента на ответ

Это ключевое понятие метода. Каждый retrieved-фрагмент может пытаться повлиять на ответ модели
по-разному, и разные виды влияния разрешены по-разному:

| Вид влияния (код) | Что это | По умолчанию |
|---|---|---|
| `content` | повлиять на фактическое содержание ответа | разрешено всегда |
| `task` | подменить задачу, которую решает модель | только если запрос это разрешает |
| `instructions` | изменить правила/инструкции модели (роль, системный промпт) | запрещено всегда |
| `disclosure` | заставить раскрыть служебные или чужие данные, секреты | запрещено всегда |
| `actions` | инициировать действие или вызов инструмента | только если запрос это разрешает |
| `format` | навязать форму ответа или вывод во внешний канал (ссылки, картинки) | только если запрос это разрешает |

Главная идея: **набор разрешённых видов влияния зависит от запроса пользователя**. Один и тот же
фрагмент легитимен для запроса «выполни процедуру из документа» (разрешены `task` и `actions`) и
недопустим для запроса «кратко перескажи» (разрешён только `content`).

## RAG-стенд

```
запрос ─▶ оркестратор
             │
   поиск (ретривер) ──▶ КОНТРОЛЬ РАЗРЕШЕНИЙ ──▶ системный промпт ─▶ LLM ─▶ постобработка ─▶ ответ
        ▲ (разбиение,              │                                  │
         эмбеддинг, индекс)        ▼                                  ▼
                               журнал                            инструменты
```

| Модуль | Файл | Назначение |
|---|---|---|
| Оркестратор | `ctxauth/rag/orchestrator.py` | собирает стенд, исполняет запрос |
| Системный промпт | `ctxauth/rag/prompts.py` | промпт + секретная метка (для проверки утечки) + spotlighting |
| Разбиение / эмбеддинг | `ctxauth/rag/chunking.py`, `embed.py` | фрагментация документов, TF-IDF или sentence-transformers |
| Векторное хранилище | `ctxauth/rag/index.py` | поиск по косинусной близости |
| Ретривер | `ctxauth/rag/retriever.py` | поиск top-k, опциональный лексический реранк |
| **Контроль разрешений** | **`ctxauth/authority/`** | **основной метод — см. ниже** |
| LLM | `ctxauth/rag/llm.py` | офлайн-заглушка или локальная модель (OpenAI-совместимый API) |
| Инструменты | `ctxauth/rag/tools.py` | регистратор вызовов (факт вызова = успешная атака на действие) |
| Постобработка | `ctxauth/rag/postprocess.py` | блокировка внешних ссылок вне allowlist |
| Журнал | `ctxauth/rag/audit.py` | JSONL-журнал решений |
| Командная строка | `ctxauth/cli.py` | запуск демо, оценки, обучения |

## Контроль разрешений (основной метод)

Четыре шага для каждого фрагмента (`ctxauth/authority/controller.py`):

1. **Что разрешает запрос** (`intent.py`): запрос пользователя классифицируется в намерение
   (перескажи / вопрос-ответ / выполни процедуру / оформи по образцу / …), каждому намерению
   соответствует набор разрешённых видов влияния. `instructions` и `disclosure` не разрешаются
   никогда. Это и есть зависимость разрешений от запроса.

2. **На что претендует фрагмент** (`rules.py` + `analyzer.py`): для каждого предложения
   оценивается, на какие виды влияния оно претендует. Учитываются: адресация к модели,
   переопределение правил, подмена задачи, запрос раскрытия, инициирование действий, навязывание
   формы/внешнего канала. Ослабляющие признаки (борьба с ложными срабатываниями): предостережения
   («never share…»), обезличенные шаги инструкций, повествование в прошедшем времени, цитирование.

   Режимы анализатора (`AuthorityAnalyzer(mode=…)`):
   - `rules` — только правила (устойчивое ядро, переносится между наборами, низкий FPR);
   - `ml` — только обучаемый скорер (`ml.py`: TF-IDF слова+символы, логистическая регрессия);
   - `max` / `mean` — комбинация правил и обучаемой модели;
   - `gated` — **рекомендуемый гибрид**: обучаемая модель усиливает правила, но в одиночку (когда
     правила молчат) учитывается только при уверенности ≥ `gate`. Это снижает ложные срабатывания
     обучаемой модели на незнакомых данных. Пороги подбираются на валидации
     (`eval/train.py: calibrate_thresholds`), а не на тесте.

3. **Нарушения**: вид влияния заявлен (оценка ≥ порога) и не разрешён запросом; либо разрешён, но
   выходит за рамки (инструмент вне `tool_scope`, ссылка вне `domain_allowlist`).

4. **Решение**: PASS / SANITIZE (вырезать нарушающие предложения) / BLOCK (целиком).
   Скрытый/обфусцированный текст и инъекции, разнесённые по нескольким фрагментам, обрабатываются
   отдельно: деобфускация в `text.py`, межфрагментный анализ в `controller.py`.

**Решение принимается без вердикта «атака/не атака»** — только по факту превышения разрешений.

## Техники инъекций и разметка

`ctxauth/taxonomy.py`: связь «техника инъекции → навязываемый вид влияния» (основа разметки
примеров) и список модулей проекта. Техники: переопределение указаний, подмена задачи, имитация
системного сообщения, запрос раскрытия, вызов инструмента, вывод во внешний канал, вставка
контента, ссылка на мнимые полномочия, плюс два модификатора — обфускация и распределение по
фрагментам.

## Оценка (`ctxauth/eval/`)

Единый интерфейс `BaseDefense.filter() → FilterResult` для основного метода и baseline'ов
(`no_filter`, `keyword`, `binary_clf`). Метрики: Precision/Recall/F1, FPR, ASR до/после,
доля удалённого чистого контекста, задержка; разрезы по виду влияния, технике, источнику.
Загрузчики бенчмарков (`ctxauth/data/loaders.py`) приводят внешние наборы к единому формату
`AttackSample` с разметкой по виду навязываемого влияния.
